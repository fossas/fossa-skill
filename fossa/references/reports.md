# Attribution reports and SBOMs

One endpoint family produces attribution reports, SBOMs, and license notices — the difference is the `format` parameter.

## Download a report

The default recipe — every section and every per-component column switched on, nothing to forget (**documented**; this is what the official CLI calls):

```
GET /api/v2/revisions/{url-encoded-revision-locator}/attribution/full/{FORMAT}
```

```bash
curl -s -m 300 -H "Authorization: Bearer $FOSSA_API_KEY" \
  "https://app.fossa.com/api/v2/revisions/custom%2B1234%2Fmy-project%24my-rev/attribution/full/CYCLONEDX_JSON" \
  -o sbom.cdx.json
```

Formats: `CYCLONEDX_JSON`, `CYCLONEDX_XML`, `SPDX_JSON` (SPDX 2.3), `SPDX3_JSON` (SPDX 3.0.1 JSON-LD), `SPDX` (tag-value), `CSV`, `HTML`, `PDF`, `MD` (markdown), `TXT` (plain text), `JSON` (FOSSA-native) — the exact values of `AttributionReportFormats` (`shared/reports/index.ts:1-13`), upper-cased by the route (`routes/revisions/reportsV2.ts:407`). `MARKDOWN` and `TEXT` are **not** accepted (400 `Invalid report format: MARKDOWN`, live-verified 2026-10-15 and again 2026-11-02). `SPDX3_JSON` **renders since CORE-7973** (FOSSA `6291388e5f`, "GA SPDX 3.0"; code at develop `b51a25a5a1`): `generateReportToStream` / `generateReportPreview` route it to the SPDX 3 builder (`modules/ReportService/index.ts:34-35, 67-68` → `modules/ReportService/spdx3/index.ts:15, 37`), and the `spdx3Export` flag is gone (no route reads it). Live-verified 2026-11-02 on org 32098: `full/SPDX3_JSON` → HTTP 200 `application/json`, one JSON-LD document with `@context` `https://spdx.org/rdf/3.0.1/spdx-context.jsonld` and a flat `@graph` (`CreationInfo.specVersion` `3.0.1`; element types `SpdxDocument`, `software_Sbom`, `software_Package`, `software_File`, `Relationship`, `simplelicensing_LicenseExpression`, `simplelicensing_SimpleLicensingText`, `Annotation`). Before CORE-7973 (develop 2026-10-27) the same call was a 500 (no renderer; live-observed 2026-10-15) — on an older deployment that is the old behaviour, not a bad request. It takes the same `dependencyInfoOptions[]` columns as `SPDX_JSON` (`shared/reports/index.ts:95-108`). One limit: a release-group report in this format cannot be published to the SBOM portal (`isPublishing` → 400 `SPDX 3.0 reports cannot be published to the SBOM portal.`, `routes/projectGroups/reportsV2.ts:353-354` — reached only after the portal-manage permission check, 403 `You are not permitted to publish reports to the portal.`, and the SBOM-portal flag check, 400 `The SBOM portal is not enabled for this organization.`, `:341-351`).

The fine-grained form is `…/attribution/download` (**documented**), where you choose the report _sections_ with `include*` flags **and must also choose the per-component _columns_** with `dependencyInfoOptions[]` — ⚠ without the column list the report has component names and nothing else:

```
GET /api/v2/revisions/{REV}/attribution/download?download=true&format={FORMAT}
    &includeDirectDependencies=true&includeDeepDependencies=true&includeNonLicenseCopyrights=true
    &dependencyInfoOptions[]=License&dependencyInfoOptions[]=OtherLicenses&dependencyInfoOptions[]=ConcludedLicense
    &dependencyInfoOptions[]=FullTextLicense&dependencyInfoOptions[]=Copyrights&dependencyInfoOptions[]=Authors
```

(`curl -g` or hand-encode the `[]` — curl otherwise treats brackets as a glob.) Other variants you will meet: `…/attribution/json` (FOSSA-native JSON; in the published spec); `full` works with or without the `/v2` prefix; the no-prefix `download` form is not in the published spec (history below).

**Why the column list is mandatory on `download`.** The v2 handler starts from an empty column set (`routes/revisions/reportsV2.ts:116`, `new Set(query.dependencyInfoOptions ?? [])`; each column maps to one option at `:163-181`), and the code itself says V1 callers who never sent it get "no license, copyright or author detail" (`:504-508`). Live-verified 2026-10-01 on org 32098: `download?format=CYCLONEDX_JSON` with only the `include*` flags → 0 of 146 components carrying a `licenses` array (SPDX_JSON: every package `NOASSERTION`); adding the six options above → 144/146 licensed, 142 with base64 license text, 71 with `copyright`; adding `includeNonLicenseCopyrights=true` as well → 83 with `copyright`, identical to `attribution/full/CYCLONEDX_JSON` (83). The copyright rule, from source: a component's `copyright` is emitted only when at least one license option is on AND `Copyrights` is on (`modules/ReportService/cycloneDx/buildCycloneDxComponents.ts:43-50`), and copyrights found in source files that are not tied to a license are merged in only when the `includeNonLicenseCopyrights` section is on (`modules/ReportService/ReportDependency.ts:365-378`; `reportsV2.ts:155`). Option names are the keys of `DependencyInfoOptions` (`shared/reports/index.ts:32-52`): `Library`, `Authors`, `Description`, `ConcludedLicense`, `License` (declared), `CustomTextLicense`, `FullTextLicense`, `LicenseTextAppendix`, `OtherLicenses` (discovered), `FilePath`, `Source`, `ProjectUrl`, `PackageDownloadUrl`, `DependencyPaths`, `IssueNotes`, `Copyrights`, `NoticeFiles`, `LicenseFileURL` (`Project` is release-group only). Two of them do nothing on this route: notice files are driven by the section flag `includeNoticeFiles=true` (`reportsV2.ts:177`), and `Library` is not mapped. `attribution/full/{FORMAT}` sidesteps all of this — `getFullReportConfig()` (`reportsV2.ts:413`; `shared/reports/utils.ts:117-166`) turns every section, including non-license copyrights, and every column on.

**Prefix history, so old advice makes sense.** The no-prefix `/api/revisions/{REV}/attribution/download` used to run a separate legacy engine over a dependency store that was being retired — on organizations already moved off it, it returned HTTP 200 with **zero components** (live-observed 2026-09-21: no prefix → 0, `/v2` → 309, `full` → 309). Since CORE-7252 (FOSSA `811be900b4`, develop 2026-09-30) the no-prefix route delegates to the same ReportService handler as `/v2` (`routes/revisions/revisions.ts:1490-1498` → `generateAttributionDownloadV3`), keeping two V1 quirks: it answers `Content-Type: application/octet-stream` + `Content-Disposition: inline` (`legacyHeaders`), and it defaults the per-component columns to the project's BOM column settings or `Library, License, CustomTextLicense, OtherLicenses` (`legacyDependencyInfoOptions`, `modules/ReportService/convertFromLegacyOptions.ts:11-31`) — which is why the no-prefix form returns licenses without `dependencyInfoOptions[]` while `/v2` does not — but never copyrights, since `Copyrights` is not in the legacy default (live-verified 2026-10-01, 146-component revision, `include*` flags only: no prefix → 144 licensed, 0 with `copyright`; `/v2` → 0 licensed). Still prefer `/v2` or `full`: they are the documented forms and the only ones with per-format content types. If a project that plainly has dependencies exports an empty SBOM, check in order: the dependency cache is not `READY` yet (below); neither `includeDirectDependencies` nor `includeDeepDependencies` was passed; the organization is on a deployment that predates CORE-7252 and you used the no-prefix form. For a **release-group-wide** report (all projects in a release, async job + poll), see `policies-and-projects.md`.

Before pulling a report on a freshly scanned revision, confirm the dependency cache is ready (`GET /api/cli/{REV}/dependencies-cache/status` → `READY`, see `scans-and-issues.md`) — earlier pulls can be incomplete.

**Queue a report for download instead of streaming it** (**documented**; since 2026-10-14, FOSSA `b472212a13`) — for reports too slow to render inside one request (large PDFs). The email-report route takes `delivery=download`, stores the finished report instead of mailing it, and returns the queued task plus the id to fetch it with:

```
GET /api/v2/revisions/{REV}/attribution/email?delivery=download&format=PDF&includeDirectDependencies=true&includeDeepDependencies=true&…
  → { "id": 12345, "jobToken": "<uuid>", "status": "CREATED", "task": "GenerateRevisionReport", …, "reportId": "<uuid>" }
GET /api/jobs/status?jobs[]={jobToken}
  → { "jobs": { "<jobToken>": { "status": "created"|"running"|"finished"|"failed" } } }
GET https://app.fossa.com/attribution/{reportId}?download=true        # NOT under /api
  → 302 to a short-lived signed S3 URL (follow it with curl -L)
```

- `delivery` is validated on the `/v2` email route only (`routes/revisions/revisionsValidators.ts:53-55`, enum `email|download`, default `email`); the no-prefix `/api/revisions/{REV}/attribution/email` still uses the old validator and always emails (`routes/revisions/revisions.ts:1260-1266`). The route stamps a fresh `reportId` on the job (`reportsV2.ts:794-812`) and the job stores the report under it and skips the email (`faktory/jobs/reports/GenerateRevisionReport.ts:33-35, 181-186`). The same `include*` / `dependencyInfoOptions[]` rules as `download` apply — it is the same query shape.
- Poll `GET /api/jobs/status` with the `jobToken` (`routes/jobs.ts:28-53`; `jobs[]` must be GUIDs or the whole call 400s). This is what the dashboard's job toaster polls (`app/hooks/api/jobs/usePollJobs.ts:13`, fed by the job `useQueueReportDownload.ts` registers).
- The fetch URL lives outside `/api`: `/attribution/{reportId}` looks the report up by uuid, allows it when it is public or you are in its organization, and redirects to a signed URL (`routes/reports.ts:64-83`; `download=true` sets the attachment filename). **An unknown or not-yet-stored id does not 404** — the route falls through to the web app, so an authenticated call gets HTTP 200 with the dashboard's HTML and an anonymous one a 302 to the login page (live-verified 2026-10-15). Check the job status first, then expect a `302` with a `Location` header; treat `text/html` as "not ready".
- The release-group routes accept the same `delivery=download` (see `policies-and-projects.md`).

Choosing:

- **Complete per-component data in one call** (license id + full license text + copyright + supplier) → `attribution/full/CYCLONEDX_JSON` (or the `download` form above with the full column list **and** `includeNonLicenseCopyrights=true` — drop the column list and the components carry no license at all; drop the non-license-copyright flag and roughly one copyright in seven goes missing, silently). License text arrives **base64-encoded** in `components[].licenses[].license.text.content`; copyright in `components[].copyright`. SPDX_JSON also carries texts but in a side table (`hasExtractedLicensingInfos`), which is more work to join.
- **Human-readable notices file** → `HTML`, `MD`, `TXT`, or `PDF`.
- **Spreadsheet triage** → `CSV`.

Flags that bite:

- `includeDeepDependencies=true` is required for transitive dependencies — without it you get direct-only and a report a fraction of the real size (verified: 121 of 309 components).
- **CycloneDX embeds whatever license text FOSSA has for each listed license; `FullTextLicense` does not change it.** A dependency carries `licenses` only when a license column puts them there (`License`, `OtherLicenses` or `ConcludedLicense` on `download`; `full` turns them all on; with none of them dependencies have no `licenses` array, see above), so for dependencies dropping those columns is the only server-side lever, and it drops the license ids too. The root component's own licenses follow the section flags instead (see the root-component entry below). Code at FOSSA master `bc89664365`:
  - **Why the option is a no-op.** `generateCycloneDxReport` re-registers the license hydrator with `includeLicenseText: true` whatever the report options say (`modules/ReportService/cycloneDx/index.ts:29-33`; `withLicenses` replaces the hydrator by name, `modules/DependencyManagerV3/index.ts:375-376`), overriding the `fullLicenseText || licenseHeaders` gate the other formats use (`modules/ReportService/getDepManagerForReport.ts:103`). `buildLicenses` then writes each dependency license's text as `licenses[].license.text`, an object whose base64 payload is `.content` (as above), with `contentType: text/plain` (`modules/ReportService/cycloneDx/buildCycloneDxComponents.ts:151-159`; the root component's licenses at `buildRootComponentLicensing.ts:30-34`). Dropping `FullTextLicense` or `CustomTextLicense` from `dependencyInfoOptions[]` therefore leaves the file unchanged, and the report UI does not offer the column for CycloneDX (`shared/reports/index.ts:98`). If FOSSA's CycloneDX export ever starts honouring Full License Text, `cycloneDx/index.ts:30` is the line that changes.
  - **Live, 2026-11-04, org 33496.** `attribution/full/CYCLONEDX_JSON` for 58 revisions: 16,273 of 17,200 license entries carry text, every one base64 (the rest are `public-domain` and `unknown`, whose catalog text is empty), and that text is 70% of the bytes (164.6 of 234.2 MB; 92% on a container SBOM). `download` without `FullTextLicense` and `CustomTextLicense` returned the same text byte for byte, in JSON and XML.
  - **Encoding (CycloneDX), and shrinking the file.** Included license text in CycloneDX is always base64; no report option writes it as plain text, though the CycloneDX schema makes `encoding` optional (only `content` is required on an attachment). A CycloneDX-only option to write it as plain text, defaulting to base64, is requested in CORE-8175 (in XML, a text containing a form feed, which XML 1.0 cannot carry, would stay base64); the encoding is set in `buildCycloneDxComponents.ts:151-159` and `buildRootComponentLicensing.ts:30-34`. Until then, decode a JSON export client-side (jq 1.6+ for `@base64d`): `jq '(.. | objects | select(.text?.encoding? == "base64") | .text) |= (.content |= @base64d | del(.encoding))'` (live: 1,719 texts decoded, each identical to the base64 decoded in Python, `contentType` kept, nothing else changed; 18.6 MB → 14.4 MB). It edits each attachment in place, so other keys survive and a third-party file without `contentType` doesn't gain one. To drop the text instead: `jq 'del(.. | objects | select(.text?.encoding? == "base64") | .text)'` (18.6 MB → 1.2 MB, nothing else changed). Both are safe because in FOSSA's CycloneDX output only license texts carry `encoding: base64`.
  - **Which text.** The embedded text is the dependency's stored license text (`RevisionLicenses.text`, `modules/LicenseManager/hydrateLicenseForDependencies.ts:94`) when there is one, which is not always the canonical license: a dependency can carry a short notice (Jackson's 321-character Apache 2.0 notice) or a file header (`SPDX-License-Identifier: MIT`). A dependency license with no stored text gets the license catalog's text (`modules/ReportService/ReportDependency.ts:732-740`). The root component's own licenses fall back to the license's standard header instead (`makeAttribution`, `buildRootComponentLicensing.ts:30`; `modules/licenses/utils.ts:133-145`), so the same license id can carry a short header at the root and the full text on a dependency.
- **Vulnerabilities are opt-in on `download`**: add `includeOpenVulnerabilities=true` (and `includeClosedVulnerabilities=true` if wanted; `includeVulnerabilities=true` switches on both) to get the CycloneDX `vulnerabilities[]` array, one entry per CVE that is still open on some component (state `affected`, or `exploitable` with the spec vocabulary) plus one per (ignore reason, distinct note), so with both flags on a CVE open on one version and triaged on another gets both an open entry and an ignored entry whose state follows the reason (`not_affected`, or `fixed` / `under_investigation`, `resolved` / `in_triage` with the spec vocabulary, as mapped below); `includeOpenVulnerabilities` alone leaves the ignored entries out and `includeClosedVulnerabilities` alone the open ones (`modules/ReportService/cycloneDx/buildCycloneDxVulnerabilities.ts:75-77`; `includeVulnerabilities=true` sets both, `routes/revisions/reportsV2.ts:256-257`, `:270-271`); every entry carries all the components the CVE touches, open and ignored (`buildCycloneDxVulnerabilities.ts:96-99`, `:353-395`; count `[.vulnerabilities[]?.id] | unique | length` for distinct CVEs; the `?` keeps it at 0 instead of an error when the export has no `vulnerabilities` key, and 0 means the export carried none, not that the revision has none) with CVSS rating and `analysis.state`. `attribution/full` includes them without flags. Only CycloneDX carries vulnerabilities — SPDX exports have no vulnerability section — and FOSSA leaves them out for organizations below the premium tier.
  - **VEX vocabulary: FOSSA's own names by default, the CycloneDX spec's on request** (code at FOSSA master `b0c4f460cf`, 2026-11-04). By default `analysis.state` is `affected` for an open issue, `fixed` or `under_investigation` for an issue ignored with those reasons and `not_affected` for every other ignore, and `analysis.justification` is FOSSA's ignore-reason string verbatim (`Vulnerable_code_not_in_execute_path`, `Inline_mitigations_already_exist`, …, `shared/issuesV2/vex.ts`); the builder's own words are "Legacy behavior: pass raw VulnIgnoreReason string as justification (non-spec-compliant, matching legacy output)" (`modules/ReportService/cycloneDx/buildCycloneDxVulnerabilities.ts:355-396`; the three non-spec states are `CortezCustomVulnState`, `modules/sbom/cyclonedx/types.ts:7-11`). Since CORE-7192 (FOSSA `9cad098136`, 2026-09-10, first tag 4.34.102) `download` takes `shouldUseCycloneDXVulnAnalysisState=true` (`routes/revisions/reportsV2.ts:181`, parsed with `isTrue` at `:278`; release groups `routes/projectGroups/reportsV2.ts:116`, `:230`; the no-prefix form maps it too, `modules/ReportService/convertFromLegacyOptions.ts:96`; it is the report UI's "CycloneDX Vuln Analysis State" checkbox, `app/components/projects/generic/ReportGenerationV2/utils.ts:174-182`). With it on, states map `affected` → `exploitable`, `fixed` → `resolved`, `under_investigation` → `in_triage` (`modules/sbom/cyclonedx/vulnState.ts:29-40`) and reasons map `Vulnerable_code_not_present` → `code_not_present`, `Vulnerable_code_not_in_execute_path` → `code_not_reachable`, `Inline_mitigations_already_exist` → `protected_by_mitigating_control`, `Vulnerable_code_cannot_be_controlled_by_adversary` → `requires_environment`. Only those four VEX reasons get a `justification`: `Component_not_present` is unmapped on purpose, and `incorrect_data_found`, `other`, the fixed and under-investigation reasons and the auto-ignore reasons have no CycloneDX equivalent, so those entries carry `state` and `detail` only (`vulnState.ts:8-20`, `:42-51`; the reason catalogue is `shared/issuesV2/common.ts:281-360`; applied at `buildCycloneDxVulnerabilities.ts:374-385`). `full` never emits the spec values (`getFullReportConfig` leaves the toggle off deliberately so existing consumers keep the states they parse, `shared/reports/utils.ts:43-45`, `:141`), so use `download` with the full column list:

    ```bash
    ( set -o pipefail
    curl -sSgf -m 300 -H "Authorization: Bearer $FOSSA_API_KEY" \
      "https://app.fossa.com/api/v2/revisions/{REV}/attribution/download?download=true&format=CYCLONEDX_JSON&includeDirectDependencies=true&includeDeepDependencies=true&includeNonLicenseCopyrights=true&includeHashAndVersionData=true&includeProjectLicense=true&includeLicenseScan=true&includeNoticeFiles=true&includeSupportStatus=true&includePackageLabels=true&includeSnippetDependencies=true&includeVulnerabilities=true&shouldUseCycloneDXVulnAnalysisState=true&dependencyInfoOptions[]=License&dependencyInfoOptions[]=OtherLicenses&dependencyInfoOptions[]=ConcludedLicense&dependencyInfoOptions[]=FullTextLicense&dependencyInfoOptions[]=Copyrights&dependencyInfoOptions[]=Authors&dependencyInfoOptions[]=Description" \

    )
    ```

    Eight more switches than the column list at the top of this file, because the dependency manager and the CycloneDX builders read them: `includeHashAndVersionData=true` is what gives components a `version` (`modules/ReportService/cycloneDx/buildCycloneDxComponents.ts:57-59`; `routes/revisions/reportsV2.ts:178`; `full` sets it, `shared/reports/utils.ts:138`); `Description` fills `description` (`:60-62`; `reportsV2.ts:185`; `utils.ts:149`); `includeProjectLicense` and `includeLicenseScan` give the root component its licenses (`reportsV2.ts:163-164`); `includeNoticeFiles` the root notice properties and each component's `noticeFiles` (`reportsV2.ts:161`, `:198`; `buildCycloneDxComponents.ts:215`); `includeSupportStatus` the support-status properties (`reportsV2.ts:172`; `buildCycloneDxComponents.ts:199`); `includePackageLabels` the `packageLabels` property (`reportsV2.ts:196`; `buildCycloneDxComponents.ts:207-211`); `includeSnippetDependencies` adds snippet-matched components (C/C++ revisions scanned with `--snippet-scan`): it reaches the output through the dependency manager's source filter, not the CycloneDX builders (`reportsV2.ts:260`, `:167`; `modules/ReportService/getDepManagerForReport.ts:179-181`); `full` sets every one of them (`utils.ts:119-166`, snippets at `:127`). `PackageDownloadUrl` is not read by those builders (the CycloneDX generator pins `includeDownloadUrl: false`, `modules/ReportService/cycloneDx/index.ts:27`), so it changes nothing here. `-f` fails the call on a 4xx instead of tallying its error body, `-S` makes curl print that failure, and `set -o pipefail` in the subshell makes the pipeline's exit status carry it (jq exits 0 on empty input and prints nothing, not even the fallback, so without it a failed download looks like success to a calling script). Below the premium tier the call still succeeds: `download` has no subscription check (`reportsV2.ts:828-835`; compare `verify_subscription('premium')` on `/attribution/json` at `:770`), FOSSA switches the three vulnerability flags off for the CycloneDX formats (`:323-327`), and an export with no vulnerabilities leaves the key out (`modules/ReportService/cycloneDx/buildCycloneDxBom.ts:201-202`), so the `//` fallback means zero vulnerabilities or an organization below premium, not proof of zero.

- **Trimming by label**: `excludeLabeledDependencies=true` (CORE-7346, FOSSA `1cb66b6560`; code at develop `b51a25a5a1`) drops every dependency that carries **any** package label — the complement of a label _filter_ — and `excludeUnknownDependencies=true` drops unresolved ones. Both default to off, so labeled and unknown dependencies are in every report unless you say otherwise (`shared/reports/index.ts:147-158`; parsed with `isTrue` at `routes/revisions/reportsV2.ts:277`, applied as a toggle at `:180`; the release-group routes read the same key, `routes/projectGroups/reportsV2.ts:115, 229`; `full` leaves both off, `shared/reports/utils.ts:41-42`, `:139-140`). Live 2026-11-02 on org 32098: `download?…&excludeLabeledDependencies=true&format=CSV` → 200; the probed revision has no labeled dependencies, so the trimming itself is code-traced, not observed.
- Large reports take time to assemble — parts of report generation run 30–60s. Use a generous curl timeout (`-m 300`) and treat a slow response as normal, not failure.
- **Scope difference vs the dependencies API**: attribution reports include first-party components (your own modules); the dependencies API returns third-party only. If you feed a compliance tool, filter your own namespace out of the report (by purl namespace or supplier) rather than being surprised by the count difference.
- **The root component carries the project's own licensing** (CORE-7693, FOSSA `13237af3ea`, develop 2026-10-01; code anchors below at that SHA except the two SPDX-column anchors, which are at develop `5a248a1963`; live-verified 2026-10-28 on org 32098: `attribution/full/CYCLONEDX_JSON` root `metadata.component` carries `licenses[]` + `copyright`, `download` adds them with `includeLicenseScan` and omits them without either license flag — the probed project's license is discovered, so the `includeProjectLicense` → declared path is code-traced, `selectRootLicenseGroups.ts:13`). Which pieces appear follows the *section* flags, not `dependencyInfoOptions[]` (exactly so for CycloneDX; the SPDX exception follows): `includeProjectLicense` → declared licenses, `includeLicenseScan` → discovered licenses, `includeNoticeFiles` → notice files, `includeNonLicenseCopyrights` → copyrights found outside licenses (`routes/revisions/reportsV2.ts:141-155`; `modules/ReportService/selectRootLicenseGroups.ts:12-15`); `attribution/full` turns them all on (`shared/reports/utils.ts:117-134`). The SPDX root additionally picks up two `dependencyInfoOptions[]` columns — `FullTextLicense` (plain SPDX id vs `LicenseRef-…` plus extracted text, `modules/ReportService/spdxShared/licenseResolution.ts:103`) and `Authors` (→ `packageFileName`, `modules/ReportService/spdx/buildSpdxRootPackage.ts:98`), both at develop `5a248a1963`. Per format:
  - **CycloneDX, project report**: `metadata.component` gains `licenses[]` (declared + discovered, de-duplicated by id, base64 text, never marked concluded), a newline-joined `copyright`, and one `properties[]` entry per notice file, `null` when there are none (`modules/ReportService/cycloneDx/buildRootComponentLicensing.ts:16-56`, wired at `buildCycloneDxBom.ts:51-56`). Before this the root was an unlicensed shell — on an older deployment that is the old shape, not a scan failure.
  - **CycloneDX, release-group report** (root components exist only with `includeFOSSADependencies=true`, `buildCycloneDxBom.ts:45-47`): these roots **already carried `licenses[]`** before CORE-7693, ungated by section flags and with concluded licenses acknowledged `Concluded` (`git show 13237af3ea^:modules/ReportService/cycloneDx/buildRootProjectComponents.ts:49-50,79-104`). Since CORE-7693 they appear only under `includeProjectLicense` / `includeLicenseScan`, are never marked concluded, and gain `copyright` and notice `properties[]`. A release-group report pulled with `includeFOSSADependencies` but without the two license flags therefore **loses** its root licenses — add the flags, don't blame the scan.
  - **SPDX**: the root package's `licenseDeclared` and `copyrightText` are filled instead of the old hard-coded `NONE`. `licenseDeclared` is `NOASSERTION` when `includeProjectLicense` is off and `NONE` when there is no *declared* license (discovered ones surface only in `licenseInfoFromFiles`); `copyrightText` is `NOASSERTION` only when `includeProjectLicense`, `includeLicenseScan` and `includeNonLicenseCopyrights` are all off — otherwise it reflects just the sources that are on, so `NONE` with only `includeProjectLicense` does not rule out non-license copyrights. `licenseConcluded` is always `NOASSERTION`. Notice files and (with `includeFileMatches`) license files attach as `hasFiles`, and discovered licenses as `licenseInfoFromFiles` (`modules/ReportService/spdx/buildSpdxRootPackage.ts:33,62-70,83-92`).

## Report data quality checks

- Coverage is real but not 100% — expect some components without copyright text (extraction depends on what's in the package source). Missing copyright ≠ missing license; check them separately.
- **Vendored/archive-uploaded components** are part of the dependency sections on both `/v2` `download` and `full` (the report engine has included them alongside managed dependencies since July 2026). If a vendored component is missing, check that the org's vendored-dependency detection is enabled before suspecting the report.

## Reading attribution from the CLI

`fossa report attribution --json --project <p> --revision <r> --timeout 300` returns the FOSSA-native JSON. When projecting licenses from it, union **both** fields — registry-declared licenses live in `directDependencies[].licenses`, while licenses _discovered by scanning_ (vendored code, license files) live only in `directDependencies[].otherLicenses`:

```bash
fossa report attribution --json -p <project> -r <revision> --timeout 300 \
  | jq -r '.directDependencies[]? |
      "\(.title // .package) \(.version // "") -> \(( [(.licenses[]?.name), (.otherLicenses[]?.name)] | unique | join(", ")))"'
```

Projecting only `.licenses` makes correctly-scanned vendored dependencies look license-empty — a classic false "detection failed" conclusion.

## Structured dependency list (no texts, machine-friendly)

For a paginated, structured third-party dependency list (locator, declared/discovered licenses, depth, ignored/unknown flags) without license/copyright texts:

```
GET /api/v2/revisions/{url-encoded-revision-locator}/dependencies?count=100&page=1
```

- **The server clamps page size to [25, 100]** regardless of what you ask (`count=500` returns 100; `count=10` returns 25). Always loop pages until you've collected `total`.
- Server-side filters (flat params): `fetchers[]`, `licenses[]` (e.g. `Apache-2.0`), `depth[]` (direct|transitive), `hasIssues[]` (hasVulnIssues|hasLicensingIssues|hasQualityIssues|noIssues), `resolved`, `exactLocators[]` (exact) vs `locators[]` (substring), `layerDepth[]` (**base|other** for container layers — the issues API spells it `containerLayers[]=baseLayer|otherLayer`), `sources[]` (managed|vendored|snippet), plus hydration flags `includeLicenseText`/`includeCopyright`/`includeDownloadUrl`. Filtered `total` comes back in the body — use it instead of client-side counting.
- Two newer params (code at develop `b51a25a5a1`): `excludeAnyPackageLabel=true` — **list route only** (`routes/dependenciesV2/index.ts:53-54`, through `filterValidator`; `shared/dependenciesV2/filterSchema.ts:44-47`, CORE-7346 — the per-label form is `excludePackageLabels[]`) drops every labeled dependency; the single-dependency `GET …/dependencies/{url-encoded dep locator}` parses only hydration options plus `revisionScanId` (`:171-172`) and silently ignores it, so to ask "would this one be dropped?" call the list with `exactLocators[]=<dep>&excludeAnyPackageLabel=true` and see whether it comes back. `revisionScanId=<int>` is accepted by both routes (`:53-67`, `:172-174`) and reads the per-dependency issue data (`hasIssues[]`, inline issue flags) from that issue scan instead of the revision's latest (`shared/dependenciesV2/common.ts:33-40`, CORE-7710, FOSSA `6beef1a72e`; **documented**, `docs/swagger/parameters/dependencies/revisionScanId.yaml`). An id that is not one of this revision's scans fails the whole call with 404 `Revision Scan not found: <id>` (`code: 2004`; `routes/dependenciesV2/validators.ts:36-53`; live-verified 2026-11-02 on org 32098 with `revisionScanId=999999999`). Live 2026-11-02: `excludeAnyPackageLabel=true` → 200 with the same `total` on an unlabeled revision.
